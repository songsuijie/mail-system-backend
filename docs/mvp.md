# 第一版 MVP 功能范围说明

## 1. 项目目标

本项目是一个面向课程实训的邮件系统后端项目。第一版 MVP 的目标不是实现完整企业级邮件平台，而是完成一个结构清晰、可运行、可测试、可演示的基础邮件收发闭环。

第一版应优先证明以下能力：

1. 用户可以注册并登录系统
2. 登录用户可以向另一个已存在用户发送邮件
3. 收件人可以在收件箱看到收到的邮件
4. 发件人可以在已发送列表看到自己发出的邮件
5. 发件人和收件人可以查看有权限访问的邮件详情
6. 收件人可以区分邮件的未读和已读状态
7. 收件人可以对收件箱邮件进行逻辑删除
8. 后端接口、数据库和代码结构具备后续扩展空间

第一版采用同一系统内部用户之间的站内邮件模型，暂不实现真实外部 SMTP、POP3、IMAP 服务器互通。

## 2. MVP 范围

### 2.1 用户模块

必须实现：

- 用户注册
- 用户登录
- 获取当前登录用户信息

基本要求：

- 用户名应唯一
- 密码不应以明文形式存储
- 登录成功后返回 token
- 后续请求通过 `Authorization: Bearer <token>` 携带登录凭证
- 第一版可以使用简单 token 方案，不强制引入 Spring Security、JWT 或 Redis

### 2.2 邮件发送模块

必须实现：

- 登录用户填写收件人、主题和正文
- 后端校验收件人是否存在
- 后端校验主题和正文不能为空
- 发送成功后生成邮件主体记录
- 发送成功后生成收件关系记录
- 第一版只要求支持一个普通收件人

暂不强制实现：

- 多收件人
- 抄送 CC
- 密送 BCC
- 附件上传
- 邮件撤回
- 邮件群发

### 2.3 收件箱模块

必须实现：

- 查询当前登录用户收到的邮件列表
- 支持分页查询
- 不展示当前用户已经逻辑删除的收件记录

列表至少返回：

- 邮件 ID
- 发件人信息
- 主题
- 发送时间
- 已读状态

### 2.4 已发送模块

必须实现：

- 查询当前登录用户发送过的邮件列表
- 支持分页查询

列表至少返回：

- 邮件 ID
- 收件人信息
- 主题
- 发送时间

### 2.5 邮件详情模块

必须实现：

- 查看邮件标题
- 查看邮件正文
- 查看发件人
- 查看收件人
- 查看发送时间
- 查看当前用户在该邮件上的状态

权限规则：

- 发件人可以查看自己发送的邮件
- 收件人可以查看自己收到的邮件
- 其他用户不能查看该邮件
- 收件人查看邮件详情后，可以将该邮件标记为已读

### 2.6 邮件状态模块

必须实现：

- 未读
- 已读
- 收件人侧逻辑删除

状态设计原则：

- 邮件主体和收件人状态应分开存储
- 已读、删除等状态属于收件人个人状态，不应直接写入邮件主体表
- 第一版删除只做逻辑删除，不物理删除数据库记录

## 3. 第一版不做的功能

以下功能不进入第一版 MVP，除非后续明确调整范围：

- AI 邮件摘要
- AI 邮件分类
- AI 自动回复建议
- AI 垃圾邮件识别
- 语义搜索
- WebSocket 实时通知
- 复杂管理员系统
- 复杂角色权限系统
- 完整 Spring Security 集成
- Redis token 管理
- 附件上传和预览
- 邮件撤回
- 邮件群发
- 复杂文件夹系统
- 复杂垃圾箱恢复流程

这些能力可以在数据库、代码分层和模块命名上预留扩展空间，但不应阻塞第一版基础闭环。

## 4. 可选功能

以下功能可以在必做 MVP 稳定后再考虑：

- 邮件关键词搜索
- 草稿箱
- 多收件人
- 抄送 CC
- 密送 BCC
- 附件上传
- 邮件收藏
- 垃圾箱
- 邮件恢复
- 邮件标签
- AI 相关功能

如果时间有限，优先保证必做功能可以完整演示。

## 5. AI 扩展原则

项目后续可以加入 AI 能力作为加分项，但第一版不应将 AI 逻辑写死进基础邮件发送流程。

后续可考虑的 AI 能力包括：

1. 邮件内容摘要
2. 邮件自动分类
3. 邮件回复建议
4. 垃圾邮件识别
5. 语义搜索
6. RAG 邮件知识检索

推荐扩展方式：

- 新增独立 `ai` 或 `mail.ai` 模块
- 在 service 层通过接口调用 AI 能力
- 保证 AI 功能关闭时，基础邮件收发流程仍然可用
- 实时任务和异步任务分开处理，避免拖慢核心接口

## 6. 推荐实现顺序

第一版建议按以下顺序实现：

1. 完成数据库表结构和初始化 SQL
2. 完成统一响应格式和基础异常处理
3. 完成用户注册
4. 完成用户登录和简单 token 鉴权
5. 完成获取当前用户信息
6. 完成发送邮件
7. 完成收件箱查询
8. 完成已发送查询
9. 完成邮件详情查询和权限校验
10. 完成标记已读
11. 完成收件箱逻辑删除
12. 使用 Apifox 测试完整流程

## 7. 验收标准

第一版 MVP 完成时，应满足以下条件：

- 用户可以注册和登录
- 登录后可以获取当前用户信息
- 登录后可以向另一个已存在用户发送邮件
- 收件人可以在收件箱看到邮件
- 发件人可以在已发送列表看到邮件
- 发件人和收件人可以查看有权限访问的邮件详情
- 无权限用户不能查看他人邮件详情
- 邮件详情接口可以返回完整正文
- 收件人可以将邮件标记为已读
- 收件人可以逻辑删除自己收件箱中的邮件
- 已逻辑删除的收件箱邮件不再出现在普通收件箱列表中
- 所有核心接口可以通过 Apifox 或类似 HTTP 工具测试
- 数据库建表 SQL 已保存到 `sql/schema.sql`
- 接口文档已更新到 `docs/api.md`

## 8. 判断边界

当出现新需求时，按以下规则判断是否进入第一版：

1. 是否直接服务于注册、登录、发送、收件箱、已发送、详情、已读、删除闭环
2. 是否会明显增加数据库、鉴权、部署或联调复杂度
3. 是否属于 PDF 实训要求中的核心功能或加分功能
4. 是否会影响当前 MVP 的稳定性和演示完整性

如果一个功能不是基础闭环必需能力，应先标记为可选或后续扩展，不应提前实现。
